# REM 1.2.7-rc.1 Stabilization Audit

This ledger is the authoritative record for the `1.2.7-rc.1` stabilization
work. A subsystem is complete only when its code review, automated evidence,
and relevant release evidence are recorded here. Critical, high, and medium
correctness findings cannot be deferred.

## Findings

| ID | Severity | Finding | Resolution |
| --- | --- | --- | --- |
| REM-127-001 | High | RCH registration bootstrap blocked local runtime startup and left the splash overlay visible when RCH or an interface was unavailable. | Local startup now completes independently; RCH refresh runs asynchronously and logs failure. Four desktop/mobile regressions pass. |
| REM-127-002 | High | JNI exports relied on the non-unwinding ABI instead of returning a compatible failure when Rust panicked. | A reusable boundary attribute contains panics on all 85 Java exports, sets `InternalError`, and returns `1` or null. |
| REM-127-003 | High | 393 Rust error conversions discarded the original I/O, database, serialization, channel, network, or SDK error. | All conversions now retain and log causal context through a stable internal failure record; JNI consumes that context without changing `NodeError`. |
| REM-127-004 | High | npm and Rust dependency graphs contained known advisories. | Compatible lockfile updates remove active npm advisories and the RustSec `anyhow` vulnerability. Clean `npm ci`, npm audit, and cargo audit gates pass. |
| REM-127-005 | Medium | Numeric casts crossed timestamps, SQLite values, counters, coordinates, sizes, and timeout boundaries without an explicit policy. | Checked/saturating helpers and exact integer-to-float conversion replace risky casts; boundary tests pass. |
| REM-127-006 | Medium | Ambiguous boolean/argument-heavy Rust calls and ignored value-returning APIs made misuse easier. | Typed request structures and `#[must_use]` annotations added at defect-prone boundaries. |
| REM-127-007 | Medium | Vite watched generated Android/Rust/test trees, contributing to watcher exhaustion. | Generated and temporary trees are ignored by the development watcher. |
| REM-127-008 | Medium | CI ran only Playwright smoke coverage and the current-LXMF job incorrectly enforced the pinned lockfile. | CI now runs the complete Playwright matrix and creates an ephemeral current-LXMF lockfile while pinned `v0.9.5` remains locked. |
| REM-127-009 | Medium | Android services, the plugin host, SDK helpers, and sample plugins silently swallowed malformed payload, callback, and cleanup failures. | Recoverable fallbacks remain compatible, cleanup remains non-fatal, and every caught failure now records its cause at an appropriate log level. No ignored or empty production Java catch remains. |
| REM-127-010 | High | The JNI bridge held its global state mutex while performing potentially slow runtime operations. Concurrent RCH timeouts could starve settings persistence and restart, leaving the UI indefinitely on `Saving`. | Bridge state now stores an `Arc<Node>`, clones it while locked, and releases the mutex before node work. JNI last-error state is thread-local so parallel calls cannot consume one another's diagnostics. Focused Rust tests and a two-phone settings/restart regression pass. |
| REM-127-011 | Medium | The LoRa-sized checklist create envelope intentionally omitted description/start metadata, but the app never followed it with a metadata update; receivers displayed `Checklist package` instead of the sender's subtitle. | Creation now assigns the checklist UID before the native call and immediately sends the existing `checklist.update` command for description/start metadata. The compact create envelope is unchanged. Typecheck, focused Playwright, and two-phone TCP replication preserve the exact subtitle and 12 tasks. |
| REM-127-012 | High | Three stale propagation-only SOS recipients could consume every recovery semaphore permit and indefinitely starve a valid direct emergency recipient. | Direct/Auto SOS remains on the reserved `mission-recovery` lane, while propagation-only SOS uses `mission-propagation`. A Rust classification regression and a four-recipient physical test show the Pixel acquiring recovery capacity independently, receiving the alert, and acknowledging it. |
| REM-127-013 | High | Telemetry initialization occurred after fallible startup history work and the publish loop did not watch native runtime readiness. A slow or partially failed startup could leave enabled telemetry permanently `Idle` after the runtime became ready. | Telemetry now binds immediately after node-client initialization and watches `NodeStatus.running`. Typecheck and a Playwright readiness-transition regression pass; on the S8 the state changes to `Publishing`, the Pixel receives repeated `mission.registry.telemetry.upsert` records, and acknowledgements return to the sender. |
| REM-127-014 | High | The Android RNode manager inserted an interface as `connected` immediately after creating its transport context. A powered-off or unavailable paired radio therefore appeared LoRa `Ready` while every BLE/KISS setup attempt timed out and no radio packets moved. | RNode interfaces now begin as `connecting` and are promoted only when the validated runtime probe reports a detected device and online radio. Command failures are retained, and an unvalidated startup becomes `failed` with an actionable timeout after 30 seconds while retries continue. Two focused Rust regressions, all three Android ABI builds, and Pixel/S8 TCP-disabled negative-path runs keep unavailable radios out of `Ready` while the local runtime remains usable. |
| REM-127-015 | Medium | Hosted checks used the deprecated Node 20 runtime bundled with `actions/setup-node@v4`; GitHub was forcibly substituting Node 24 and annotating every run. | All workflows now use the established `actions/setup-node@v6` runtime while retaining explicit npm caching and Node.js 20 for the product build matrix. |

## Physical-device evidence in progress

- On 2026-07-19, authorized Pixel 7 `35031FDH2003N8` and Samsung S8
  `988b9b344135304639` both reported `Ready` with RNode disabled and TCP
  connected. Mutual announces were received at zero hops, and explicit peer
  connections were active before workflow sends.
- Bidirectional direct chat markers `TCP-only-rc1-1442` and
  `TCP-reply-rc1-1444` reached the opposite phone and reached acknowledged
  terminal state.
- S8 EAM state replicated read-only to Pixel. MECP event marker
  `P01 MECP-TCP-rc1` arrived on Pixel with the matching
  `mission.registry.log_entry.upsert` event UID.
- Checklist `RC1_Metadata_Check` replicated from S8 to Pixel with all 12
  template tasks and the exact subtitle `Preserved_on_Pixel`. Native logs show
  ordered `checklist.create.online` and `checklist.update` receipt and an
  acknowledgement for the metadata update.
- A fresh S8 SOS with one valid direct Pixel peer and three stale
  propagation-only peers placed only the Pixel on `mission-recovery`. The
  Pixel received the active incident with GPS and 100% battery, returned an
  application acknowledgement, and later received cancellation. An incident
  that was active before application restart was also restored and cancelled.
- With telemetry temporarily set to a five-second interval, the S8 UI reported
  `Publishing`; the Pixel repeatedly received
  `mission.registry.telemetry.upsert` with the S8 coordinates and returned
  accepted acknowledgements. The normal 1800-second interval was restored
  after evidence capture.
- Both saved RNode configurations were enabled and restarted with Wi-Fi and
  mobile data disabled. The paired peripherals did not advertise: direct BLE
  connection and fallback scan timed out on both phones. The corrected build
  reports the native interfaces as `failed` after the bounded startup timeout,
  LoRa as `Failed`, TCP as `Failed`, and the local runtime as `Ready`. This is
  an unavailable-radio negative-path pass, not a LoRa transport pass. LoRa-only,
  mixed-interface, duplicate, and soak evidence remain open until both radios
  are powered and actual packet counters advance.
