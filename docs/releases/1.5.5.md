# REM 1.5.5 candidate

This candidate implements milestone 13's telemetry reliability changes. Publication
is held until the final two-phone LoRa acceptance run, as requested by the user.

- Telemetry can initiate direct delivery from a current trusted LXMF route without
  chat, SOS or manual connection warm-up.
- Saved contacts and active local-team membership survive restart in target
  planning. Current capability observations override persisted capability data;
  removed/unauthorized recipients remain excluded. Connected hub privacy rules
  remain in force.
- Native recovery retains the latest pending fix, coalesces superseded positions,
  resumes after readiness changes/restart, and tracks each recipient independently.
  Stable command IDs and timestamp-ordered receiver persistence make retries
  idempotent at the position projection.
- Location settings distinguish local acquisition, queued delivery, transmission,
  transport receipt, application acceptance/rejection and timeout. An enabled GPS
  timer is no longer labelled as network publication.
- Malformed recognized telemetry produces typed, position-free diagnostics and a
  correlated rejected result when enough metadata exists. Settings shows the last
  receive failure. Plain chat and unrelated mission packets stay quiet.
- Patches Vitest test tooling to 4.1.12 for the October mocker advisories.
- Includes the boot-service, Watch Status radar and Vite fixes already merged into
  main since 1.5.4.

Networking stays pinned to LXMF-rs `v0.14.0` at
`7822b608f2cd2debd8170895bc580d01dda5356e`; `r3akt-map-core` stays at
`19de27f419373c543fe6154aab2a3c027938b65d`. No new npm dependency, LXMF protocol
implementation, or UniFFI contract was added. Android is the release target;
release libraries cover arm64-v8a, armeabi-v7a and x86_64 with 16 KiB alignment.

## Release gate

Run the [exact-candidate field matrix](../testing/telemetry-1.5.5-release-gate.md)
before publishing or closing the milestone's hardware acceptance criteria.
Software tests and signed packaging do not establish physical LoRa, background
Android location/permission/battery behavior, or the RCH collector/map chain.
