# REM 1.5.5

Android telemetry reliability and delivery diagnostics.

- Telemetry can initiate its own direct link using trusted saved or live team peers, without chat or manual connection warm-up.
- A bounded native outbox retains the latest fix, coalesces superseded positions and recovers after readiness changes or restart. Removed and unauthorized recipients stay excluded.
- Location settings separate local acquisition, queueing, transmission, transport receipt and application acceptance/rejection.
- Malformed telemetry produces typed, position-free diagnostics and a correlated rejection when metadata permits. Android packet logs omit encoded position payloads.
- Battery transitions enqueue community updates without blocking Android's main thread; resuming refreshes the saver badge.
- Includes the normalized-identity SOS deduplication, boot-service, Watch Status radar, Vite and Vitest fixes merged since 1.5.4.

Validation: all applicable build-source CI checks pass; 503 Rust, 56 Android JVM, 171 app, 40 client and 128 browser tests passed. Signed APK/AAB cover arm64-v8a, armeabi-v7a and x86_64, with required 16 KiB alignment and signing continuity from 1.5.4.

Physical evidence includes two-way LoRa telemetry on the earlier exact candidate, and telemetry, drone-marker creation/rename and five battery state/resume cases on the final normal Pixel candidate. Pixel used a labelled mock position where indoor GNSS was unavailable. Reverse telemetry required a retry. The user approved publication with remaining cold-radio, pre-readiness, malformed-rejection and Android scenarios tracked in [#311](https://github.com/FreeTAKTeam/reticulum_mobile_emergency_management/issues/311); these are not claimed as passed. Queued marker moves/deletions also remain unconfirmed.
