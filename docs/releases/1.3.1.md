# REM 1.3.1

REM 1.3.1 updates the compiled networking stack to LXMF-rs `v0.10.1` and
ships stricter LoRa configuration safeguards across the mobile UI,
TypeScript client boundary, and Rust/JNI runtime boundary.

## Highlights

- Align the compiled LXMF and Reticulum stack with LXMF-rs `v0.10.1` and
  RNS `1.5.2`.
- Pin CI and plugin builds to the immutable LXMF-rs release commit
  `25a976945cb335dff3be692981151c8741a5fdeb`.
- Reject unknown LoRa region and radio-profile identifiers instead of silently
  retuning them to US915 defaults.
- Enforce the RNode hardware frequency range of 137 MHz through 3 GHz at the
  UI, node-client, and native configuration boundaries.
- Prefer a current location fix over the device time zone when inferring a
  LoRa region, and require manual selection for ambiguous locations.
- Keep operators responsible for confirming that the selected region and
  frequency are legal at the deployment location.
- Retain the 1.3.0 Android BLE and Bluetooth Classic RNode transports,
  firmware compatibility path, and bearer-neutral compiled LXMF ownership.

## Compatibility

- Android API 26 or newer.
- LXMF-rs `v0.10.1`, pinned at
  `25a976945cb335dff3be692981151c8741a5fdeb`.
- RNS `1.5.2` compatibility through the pinned LXMF-rs release.
- RNode firmware `1.83` or newer is recommended for modern Android BLE
  pairing.

Physical LoRa range, mixed-interface operation, and jurisdiction-specific
frequency legality remain field acceptance items. Automated tests validate the
configuration and protocol boundaries but do not replace radio-hardware
testing.

See the [RNode Bluetooth connectivity guide](../rnode-bluetooth-connectivity.md)
for pairing, configuration, verification, and troubleshooting steps.
