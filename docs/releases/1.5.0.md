# REM 1.5.0

REM 1.5.0 adds shared map markers: operators can create, edit, move, delete and
share point markers that are not tied to a user, with the same symbol catalog
and validation rules as the Reticulum Community Hub (RCH). The compiled
networking stack is LXMF-rs `v0.14.0`, pinned to release commit
`7822b608f2cd2debd8170895bc580d01dda5356e`.

## Highlights

- **Map markers in the Map view.** One add button in the thumb zone opens a
  symbol sheet with recent symbols and the full RCH catalog grouped by
  category, with search by label or RCH alias. Placement uses a centre
  crosshair with live coordinates; long-press places the most recent symbol.
  Tapping a marker opens a details sheet with rename, move and delete. A
  "Markers" chip shows or hides the layer. Telemetry and SOS layers are
  unchanged.
- **Shared marker rules, no second implementation.** The native runtime stores
  markers through RCH's shared `r3akt-map-core` crate in the same `rch_markers`
  tables and identifiers RCH uses. Symbol normalization, validation messages,
  idempotent creation and last-writer-wins replica handling all come from the
  shared crate; REM adds no marker logic of its own.
- **Marker replication.** Each local create, rename, move or delete sends one
  LXMF message to the same targets as mission events: the hub in Connected
  mode (which applies the change and relays it to the TEAM), or saved and TEAM
  peers in Autonomous and Semi-autonomous modes. Received replicas from RCH or
  REM peers are validated the same way as local input and are never re-sent.
  One canonical `object_destination_hash` is kept everywhere.
- **Plugin map API 1.2 and 1.3.** Trusted, enabled plugins can list symbols,
  create and manage their own markers, and read an observer snapshot
  (`mapMarkersRead`, `mapMarkersWrite`, `mapObserverRead`). API 1.3 adds
  operator-selected map sessions (`mapSelectionRead`): the marker details sheet
  offers "Share with <plugin>", and a plugin reads exactly the selected objects
  and receives session events over the existing host event channel. Sessions
  are native-owned, bounded, and end on revocation, disable, uninstall, Binder
  death or node stop. Uninstalling a plugin never deletes its shared markers.
  The reference consumer is `plugins/map-fixture`; the contract is documented
  in `docs/plugins/android-plugin-system.md`.
- **Dependency alignment.** REM builds against LXMF-rs `v0.14.0` (wire formats
  unchanged from `v0.13.0`; `rusqlite` 0.40 shared with `r3akt-map-core`).
  `r3akt-map-core` is pinned to the merged RCH revision
  `19de27f419373c543fe6154aab2a3c027938b65d`.

## Known limitations

- Hub sync needs RCH permissions: the REM user needs `mission.content.write`
  on the hub (mission writer, team lead or incident commander), otherwise RCH
  rejects marker commands and does not relay them.
- There are no tombstones. A delete can be undone by an older replica that
  arrives later. This is documented in both repositories.
- The shared crate only supports rename, move and delete as edits. Symbol,
  category and notes cannot be changed after creation.
- Plugin map sessions do not survive an app restart.
- Issue #280 remains open: its integration, on-device and plugin acceptance
  checks have not been claimed complete, and automated coverage is described
  there rather than here.

## Compatibility and field-test scope

LXMF-rs v0.14.0 includes selected changes from Python Reticulum 1.5.5; it does
not claim full Reticulum 1.5.5 parity. See the
[upstream release notes](https://github.com/FreeTAKTeam/LXMF-rs/releases/tag/v0.14.0).

Android is the release target. Native libraries are rebuilt for `arm64-v8a`,
`armeabi-v7a`, and `x86_64` with 16 KiB ELF alignment. The JNI boundary used
by the Android app gains the map marker, plugin map and session methods, and
the UniFFI definition gains the matching map marker records. Generated UniFFI
bindings remain untracked and are not part of the APK.

Marker replication, hub sync and plugin sessions were validated by automated
tests and the hosted emulator plugin job, not by live two-device or
hub-connected field runs. The earlier REM 1.4 two-phone LoRa evidence does not
validate this APK. Physical-radio, mixed-interface, and two-phone acceptance
must be repeated with these exact artifacts. Known EAM and checklist
replication gaps described in [REM 1.4](1.4.md) are not claimed fixed. See the
[manual release matrix](../rem-1.2-manual-release-gate.md).
