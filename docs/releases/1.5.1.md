# REM 1.5.1

REM 1.5.1 is a fix release for the shared map markers introduced in 1.5.0.
It makes marker replication responsive and reliable between phones, replaces
the Inner Circle selection as the replication trust owner with local team
membership, and folds the map's top chips into one menu. The compiled
networking stack is unchanged: LXMF-rs `v0.14.0`, pinned to release commit
`7822b608f2cd2debd8170895bc580d01dda5356e`.

## Highlights

- **Operators must know: team membership now decides who receives your data.**
  Local team membership is now the runtime's trust owner (circles phase 1). A
  saved peer must be on the active local team to receive events, missions,
  checklists, EAM, telemetry and marker replication from this phone. Saved
  contacts who are not on the team can still chat and can still receive
  household status and SOS. The "Inner Circle" selection on the Peers page no
  longer drives replication. After upgrading from 1.5.0, check that the peers
  you expect to share operational data with are members of the active team;
  peers that are only saved contacts will no longer receive it.
- **Placing a marker no longer blocks the Place button.** In 1.5.0 each marker
  create awaited delivery to every saved peer, which held the Place button for
  about ten minutes per create when saved peers were unreachable. Replication
  is now queued: the create, rename, move or delete returns as soon as the
  local change is committed and the sends are handed to the runtime. Markers
  are delivered directly to saved peers once their identity is known, and a
  saved peer keeps its circle tier when an announce refreshes it.
- **Outbound sends can no longer starve each other.** Sends (`SendBytes`,
  `SendLxmf` and chat retries) now run outside the bounded runtime work lane,
  so a propagation send to an unreachable peer cannot hold up direct sends. On
  1.5.0 this starvation meant marker edits made on one phone could fail to
  reach the other.
- **Household profile fixes.** The household profile never blocks a Settings
  save and always has a standard name. The setup wizard defaults an empty
  household ID from the node destination.
- **One Map menu.** The map's top chips (live, stale, SOS, Markers and layers)
  are folded into a single hamburger "Map menu" with Status, Layer and Objects
  groups. Active SOS alerts show as a count badge on the collapsed button.
- **Dependencies unchanged.** LXMF-rs stays at `v0.14.0` (commit
  `7822b608f2cd2debd8170895bc580d01dda5356e`) and `r3akt-map-core` stays at
  `19de27f419373c543fe6154aab2a3c027938b65d`.

## Known limitations

- Hub sync needs RCH permissions: the REM user needs `mission.content.write`
  on the hub (mission writer, team lead or incident commander), otherwise RCH
  rejects marker commands and does not relay them.
- There are no tombstones. A delete can be undone by an older replica that
  arrives later.
- The shared crate only supports rename, move and delete as edits. Symbol,
  category and notes cannot be changed after creation.
- Plugin map sessions do not survive an app restart.
- The marker details sheet must be closed before placing the next marker.
- Known EAM and checklist replication gaps described in [REM 1.4](1.4.md) are
  not claimed fixed.
- Issue #280 remains open: its integration, on-device and plugin acceptance
  checks have not been claimed complete.

## Compatibility and field-test scope

LXMF-rs v0.14.0 includes selected changes from Python Reticulum 1.5.5; it does
not claim full Reticulum 1.5.5 parity. See the
[upstream release notes](https://github.com/FreeTAKTeam/LXMF-rs/releases/tag/v0.14.0).

Android is the release target. Native libraries are rebuilt for `arm64-v8a`,
`armeabi-v7a`, and `x86_64` with 16 KiB ELF alignment. Generated UniFFI
bindings remain untracked and are not part of the APK.

Field evidence from 2026-10-16: on a Pixel 7 and a Poco X5 Pro running
development builds of the same `main` commits, marker create, move and rename
replicated between the two phones within seconds; a marker move on the Poco
reached the Pixel in about one second. That run used development builds, not
these release artifacts. Physical LoRa, mixed-interface and hub-connected
(RCH) acceptance were not repeated for these artifacts and must be repeated
with these exact APK and AAB files. The earlier REM 1.4 two-phone LoRa
evidence does not validate this APK. See the
[manual release matrix](../rem-1.2-manual-release-gate.md).
