# REM 1.4

REM 1.4 repairs Android RNode receive and transmit handling and uses the merged
LXMF-rs `0.10.1`-compatible revision
`56ea9f06c474426b2245739e9cb5e2c325cdb1e2`.

## Highlights

- Keep one owner for each bounded native RNode read so cancelled Rust futures
  cannot consume and discard later BLE notifications.
- Buffer KISS frames across BLE notifications without requiring a complete
  frame or a 173-byte ATT MTU.
- Respect RNode firmware queue readiness before admitting another payload.
- Bind two-phone HIL evidence to the exact signed APK, signer, REM revision,
  and LXMF-rs revision installed on both devices.
- Report background event and telemetry fan-out failures per destination with
  their real native error code instead of mislabelling them as `NotRunning`.

## Field-test status

Two-phone testing on a POCO and Pixel at 915 MHz demonstrated bidirectional
LoRa transport for announces, links, small LXMF messages, and a 1 KiB Resource
payload. Mission events, telemetry, and SOS activation/cancellation also passed
in both directions.

The field test used the exact repaired LXMF-rs source tree and the REM product
source that precedes the final workflow-pin-only commit. It therefore validates
the repaired transport behavior, while the signed release artifacts are
validated separately from the final merged REM commit.

Known application-level gaps remain: EAM transmission from Pixel to POCO did
not produce an outbound message, and checklist metadata/task replication was
partial. These are not failures of the repaired LoRa byte transport and remain
follow-up work.
