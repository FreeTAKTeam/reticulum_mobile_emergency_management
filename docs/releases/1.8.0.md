# REM 1.8.0: Mission Library

This release adds a **Library** to the menu. It keeps photos and documents on the device for offline use, lets you share them directly with saved peers, and downloads files your Reticulum Community Hub (RCH) shares with your missions.

- **On Device:** import a photo or any document from the Android picker. REM copies it into private storage, hashes it, and keeps it available in airplane mode and across restarts. You can open it in another app, link it to missions, filter by type, mission or name, and remove the local copy. Importing the same file twice keeps one copy.
- **Shared With Me:** files that saved peers offer you appear here. Nothing downloads until you tap **Download**. REM checks that the offer comes from the file's verified owner, and verifies every part and the signed manifest before the file shows as on device.
- **Share:** send a file to one saved peer. Only that peer can fetch it. Shares survive restarts.
- **RCH:** **Refresh from hub** lists the files your missions allow, as metadata only. **Download** fetches one file and verifies it. If the hub runs an older RCH without the Library, REM shows the hub's answer instead of a list.

A hub download can no longer get stuck on **Downloading**. If the hub refuses it, or no answer arrives within about three minutes, the file shows **Retry**. Downloads left unfinished when REM stopped also show **Retry** after a restart. **Refresh from hub** shows the files already known while it asks the hub for the latest list.

Transfers use the Reticulum Package Protocol 0.3 (RC1) over Reticulum links. They start only when you ask, are paused in power saver, and run outside the SOS and acknowledgement lanes.

## Requirements

- Peer sharing works between REM 1.8.0 devices.
- Hub downloads need an RCH release with the Mission Library and its RPP service enabled (`RCH_RPP_TCP`). Listing works without the RPP service; downloads then report that the hub does not serve RPP.

## Qualification limits

- Automated checks pass: the native tests (store import, restart, dedupe, unsafe names, size cap, offers, hub cache, received files), the protocol tests (two-node Reticulum publish, offer, verified fetch, refusal of a peer that was not offered the file), the RCH command tests and the frontend checks.
- Tested on a device: RCH hub downloads of pictures on an Android phone over TCP, including retrying downloads that had failed.
- **Not yet tested on devices:** the Android picker and viewer, two-phone sharing over TCP and LoRa, interruption of a large file, and a full disk.
- An offer shows the sender, not the file name, until it is downloaded. The protocol's offer does not carry a name.

The qualification limits listed for [1.7.0](1.7.0.md) still apply.
